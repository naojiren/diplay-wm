# WePlay perf26：音频连续性修复

基于 perf25，保留实体左右键切歌、仪表投屏、音频输出与麦克风处理及 perf24 控制通道修复。

## 实车证据

2026-10-14 读取的下午日志覆盖 14:22–15:36 的数段使用记录（中间有未运行或日志空档），不是完整连续一下午的录音。

- 三段音乐流解码器累计丢帧分别为 84、34、96，共 214 帧；源码在输入缓冲等待 10 ms 无结果时直接丢帧。
- 音乐的 358 个活跃统计窗口中，窗口最大到包间隔的中位数为 445 ms、95 分位为 679 ms。导航 46 个活跃窗口对应为 279 ms、381 ms。这是每个约 5 秒窗口的最大值分布，不是每包平均延迟。
- 音乐接收序号缺口共 606 个；仅凭这些日志不能定位为手机、无线驱动或空口干扰。
- 活跃窗口中未见应用接收队列溢出和 AudioTrack 写入错误，但确有播放队列见底的采样。
- Android 6 没有公开的 AudioTrack underrunCount。旧版将其记为 0，且补缓冲依赖该计数增加，导致 Android 6 上恢复逻辑永远不能触发。
- 当前系统音频和 CPU 快照来自后续车机启动，不能作为下午播放时的资源占用证据。

## 修改

1. 解码器短暂忙时保留当前压缩音频帧，先释放已有解码输出再尝试提交。持续无法获得输入缓冲 1 秒才记超时，关闭流立即结束等待。
2. 音乐依据实际已写入/已播放帧判断断粮，持续见底 60 ms 后暂停并补缓冲；不清空已排队声音。修复不依赖 Android 7 API。导航在 API 23 及以下也使用此恢复机制，通话和 Siri 不增加此恢复等待。
3. 音频接收与解码/播放工作线程申请 Android 音频优先级；固件拒绝时尝试显示线程优先级，避免比现有双屏渲染线程更低。日志记录实际优先级，全部申请失败也继续播放。
4. API 23 及以下导航起播目标 200 ms、缓冲容量至少 400 ms；短于起播目标的提示音在最后一段 PCM 后最多等待 120 ms 即播放。音乐默认 300 ms（容量 500 ms）保持，通话与 Siri 的起播目标保持原处理。
5. Android 6 日志将 underrun 标为 unavailable，另记录解码重试、超时和补缓冲次数。

## 验证边界

版本 70 / `0.2.17-legacy.1-wm-ex5-perf26-audio-continuity`，包名 `com.shihab.diplay.wmex5`。
代码回归测试与 Android 构建结果随安装包归档。实际声音效果需要导航与音乐并行实车验证。
此版本不会补回无线传输中已经丢失的音频包，不承诺消除所有空口中断；没有改麦克风路由、音频焦点开关或无线频段设置。

API 核对：[Android AudioTrack](https://developer.android.com/reference/android/media/AudioTrack#getUnderrunCount()) 确认欠载计数从 API 24 才提供，pause 保留未播放数据，播放位置计数在 stop/flush 时重置。
[Android Process](https://developer.android.com/reference/android/os/Process#THREAD_PRIORITY_AUDIO) 的调度优先级受系统权限限制，因此使用有保护的回退和实际值诊断。
